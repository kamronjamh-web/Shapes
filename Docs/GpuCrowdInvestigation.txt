GPU crowd implementation and investigation

Current implementation (2026-10-10)
-----------------------------------
Large-population movement fix: cube rolling could stall permanently just before
completing a turn. The remaining requested movement exceeded the fixed 0.00001 m
completion tolerance but was smaller than a representable X/Z position step far
from the origin. Adding that movement rounded back to the same position, so gait
progress never completed. Both CPU rolling and GPU full drive shared the bug.

Completion now uses max(0.00001 m, two position ULPs) and checks a nearly completed
turn even when the final displacement rounds to zero. Actual displacement still
drives orientation/progress; blocked mid-roll cubes retain their unfinished gait.
The parent crowd_contacts shader changed too, ensuring the included drive code
is reimported. Rendering, spawn spacing, speed settings and collision rules remain
the same.

Native 50,000-body reproduction: after 150 ticks at 30 Hz, 2,410 bodies moved less
than 0.05 m over the final 30 ticks; 1,684 had exactly unchanged positions. All
2,410 resumed when rolling was disabled. After the fix all 50,000 moved at least
0.05 m during that interval. 100 actual GPU render-buffer origins exactly matched
authoritative visual poses, ruling out stale rendering in this reproduction.
Artifacts: .tmp/horde-spawn-movement/baseline-oldgpu and
.tmp/horde-spawn-movement/final-cleanup. The baseline's
GPU shader was the cached old version; its CPU comparison had already received
the fix, so that CPU result is not an unfixed CPU baseline. These are movement
correctness diagnostics, not frame-rate or sustained combat benchmarks.
CPU motion validation passes 76 checks; native GPU runtime passes 82,657 checks.
Four large-coordinate cardinal/diagonal cases each complete 100 rolling cycles,
with zero paired single-step CPU/GPU position/contact error. Terminal residuals
recover without advancing genuinely blocked mid-roll bodies; origin/512-boundary
tolerance cases also pass. Final build and runtimes exit cleanly without leaks.


Revised optimization target: 50,000 enemies, 1920x1080, about 45 FPS, with
GTX 1060 / RX 580 class dedicated GPUs in mind. This supersedes the earlier
100,000/60 FPS target; historical measurements below retain their actual counts.
The user wants horde variety centered on explosive chaos and chain reactions.
Those enemy mechanics are under investigation, not implemented by this note.
The user's established baseline is 10,000 enemies
at 1080p/60 FPS. Local diagnostics use the available RTX 4070 / i9-14900KF;
those measurements do not establish performance on the target older hardware.

Fort callbacks now use a cached 8 m XZ uniform grid. Solid/ramp masks and
conservative swept queries preserve narrow-phase math and geometry order.
Geometry rebuilds replace the index; unsupported counts retain full scans.

The live GPU backend runs known-fort targeting, steering, movement gait, gravity,
world constraints, one contact/piling pass and rolling. Terrain support,
ceilings, nearby fort walls/ramps and live gates share the GPU world solver.
HillFort_Horde.tres enables
it for North Gate; generic FpsHordeSettings defaults remain disabled. The grave
menu's Crowd contact tab exposes "GPU crowd contacts"; existing telemetry shows
CPU/GPU, marks fallback and exposes its reason on hover. Off/on permits failure
recovery, including while paused.

Headless, non-Vulkan, legacy/non-fort worlds, unsupported geometry, multiple
contact passes, disabled soft contacts, mismatched crowd/fort bounds and GPU
failures use CPU contacts. Failures latch instead of retrying each frame.
Persistent device/buffers are disposed with the crowd. All live results are
validated before authoritative state changes. Positions return synchronously
before attacks and weapons; immediate deaths/generation-safe handles persist.

Known-fort drive captures pure objective/routing callbacks and live global state.
Generic callbacks retain CPU execution. Full drive validates contact and drive
packets together before updating any Enemy records; failure runs original CPU
movement, contacts and rolling once from the unchanged state. CPU attacks and
visibility rays, weapons, health, deaths/corpses/loot remain in their existing
order. This is not a fully GPU-resident simulation: combat still consumes a
synchronous local-device readback each simulation step.

GPU hash buckets retain only the highest budget*8 slots in descending order.
Every rejected/self/colliding-hash candidate consumes the global scan limit, so
the discarded tail is unreachable even when a query revisits a bucket. This
bounds sorting work without changing neighbor selection or contact budgets.
Extremely concentrated buckets still have a serialized sorting cost.
CPU boundary packing uses direct struct fields; full-drive results use one
paired validation pass and one combined snapshot/application pass. Validation
still precedes all authoritative writes. Attack cooldowns skip range arithmetic
while retaining live callback order and the original distance rounding.

GpuCrowdRenderer dispatches poses on the MAIN RenderingDevice directly into
Godot-owned MultiMesh buffers, with no production pose readback or forced wait.
Raw body snapshots upload only when authoritative state changes. Interpolation,
quaternion/basis evaluation, ceiling limits and hit flashes run once per body
each render frame, independent of mesh vertex count. Explicit bounds retain
culling. CPU/GPU transitions clear Godot's native per-instance transform cache.
Do not use individual MultiMesh CPU transform getters to inspect GPU poses;
the validation-only raw GPU readback inspects actual rendering storage.

The independent "GPU crowd rendering" toggle is enabled for North Gate; generic
settings default off. Unsupported visual worlds, headless/non-Vulkan, TAA,
temporal upscaling, motion-vector debug and scene compositor effects requiring
motion vectors use the CPU bulk renderer. Raw RenderingServer-created viewports
or effects cannot be inspected automatically; callers using motion vectors must
disable GPU crowd rendering. Opt-in asynchronous main-device timestamps measure
the pose interval; viewport drawing timing is a separate, potentially overlapping
scope. Production keeps this timing instrumentation disabled.

North Gate now reserves 100,000 enemy slots. Grave/backtick > Population accepts
1-100,000 with Add/Replace/Clear and presets through 100,000. The default first
wave remains 100 cubes. Large manual formations use disjoint cardinal wedges;
Add checks occupied neighboring cells and reports successful registrations.
Oversized bodies or smaller edited maps can exhaust space before the slot limit.
Configured wave sizes and their existing per-spawn limits remain unchanged.

The runtime GPU body buffer covers the highest live slot, including holes,
rounded from 256 up to the reserved capacity. It grows on demand and shrinks
when the required span falls to one quarter of the allocation. Thus a fresh
100-body wave packs 256 slots, not 100,000. The contact hash grid retains its
reserved-capacity size to preserve CPU bucket ordering and neighbor budgets;
100,000 reserved slots mean 524,288 buckets. Live-slot bitsets skip empty
64-slot blocks while preserving ascending iteration and callback mutations.
Highest live slot is maintained on spawn/death/clear rather than searched each
step. GPU packing still writes every slot in its prefix, including holes.

CPU fallback render publication fills reused transform/color/custom-data arrays
and uploads once per occupied role. Role MultiMeshes grow from 256 toward reserved capacity
and shrink at the quarter-size threshold. Rendering, contacts, movement and
attacks traverse live slots. The combined CPU world resolver reuses terrain,
support and nearby-structure candidates; XZ changes requery support/candidates.
Existing ordered collision rules, gates, visual interpolation and hit flashes
remain intact. CPU packing/application, combat queries and reserved GPU hash
clearing remain costs. This is not a sustained 100,000-enemy combat performance claim.

Purpose and scope
-----------------
This opt-in experiment asks whether the existing bounded crowd contact/piling
pass benefits from GPU compute, including the cost of returning authoritative
positions to the CPU. At this earlier stage gameplay used the CPU solver;
the contact-only experiment had not become a live backend or raised the limit.
The existing crowd is drawn on the GPU through MultiMesh; its simulation and
render-transform preparation run on the CPU. GPU rendering alone does not make
the simulation GPU based.

Box3D is a separate CPU rigid-body engine using multithreading and SIMD. Its
sample graphics backends are for rendering, not a GPU physics solver. It was
not integrated or benchmarked here; corpse/ragdoll physics is a separate choice.

What runs on the GPU
-------------------
GpuCrowdKernel owns a local RenderingDevice and persistent buffers. Every call
uploads a frozen body snapshot, clears hash bucket heads, inserts live bodies
into the 3D contact grid, sorts bucket chains into the CPU's traversal order,
then computes one Jacobi contact/piling pass. Matching order matters because
accepted-neighbor and scanned-neighbor budgets bound the solver's work.

The shader implements rounded-body horizontal response, compression pressure,
support while falling, climbing and the pile-height cap. Each body carries its
position/radius, previous position/height, desired velocity/pressure, sampled
ground/support, vertical velocity and alive flag. Results contain proposed
position, pressure and vertical velocity. CPU packing samples world support;
CPU application resolves proposed movement against the actual world callbacks.

CPU responsibilities remain movement/AI, gravity before contacts, rolling,
terrain/fort/gate constraints, attack visibility physics rays, weapons, health,
death/corpse/loot events, identity and MultiMesh transform preparation/uploads.
The GPU draws the instances during normal gameplay. The probe explicitly
requires one enabled soft-contact iteration; it does not cover the full tuning
range of one to four iterations or the contacts-disabled separation path.

Method and interpretation
-------------------------
The NorthGate scene supplies real approach and deliberately staged gate-pressure
snapshots at the requested populations. Each population starts with a fresh
seeded scene, disabled before entering the tree to prevent uncontrolled ticks.
Each matched comparison restores the same snapshot, alternates CPU/GPU execution
order and excludes state restoration,
shader compilation and buffer allocation. GPU total includes packing, upload,
dispatch plus wait, readback, and application including world constraints.
Primary measurements are wall time, not whole-game FPS. The scaling follow-up
also records a separate Vulkan GPU timestamp interval for the four compute
phases and barriers. GPU timestamps do not measure occupancy or isolate the
cause of scheduling/contention variability.
Reported p50 and p95 use nearest-rank percentiles. Per-sample CSV records CPU
processor IDs to help diagnose scheduling effects on hybrid processors.

The separate advancing CPU profile includes movement, contacts plus rolling,
and attacks; the matched contact comparison excludes rolling on both paths.
Edge fixtures and fort snapshots compare positions, pressure, vertical velocity
and pile diagnostics against the CPU solver, with tolerance 0.001. A separate
mixed-size cluster evolves CPU/GPU states independently for 32 contact passes.
It excludes movement, gravity integration and weapons. These checks do not
establish long-run full-game trajectory or live-combat parity.

The additional repeated-dispatch measurement submits 32 groups using unchanged
input and no readback. It estimates amortized fixed-input kernel throughput.
It does not advance simulation or demonstrate an achievable gameplay frame time.

GPU timestamp implementation note
---------------------------------
Markers surround the compute list and are read immediately after local Submit/
Sync, before readback. Each submission has unique marker names; missing,
duplicate, zero or reversed pairs fail the run. Frame IDs alone are unsuitable
because several submissions can occur without a rendered frame.

On the tested Godot ed1daf0bf Vulkan implementation, driver query values are
converted with Vulkan timestampPeriod to nanoseconds and the RenderingDevice
getter does not rescale. The probe divides by 1,000,000 for milliseconds,
despite the API documentation describing microseconds. The implementation
rejects other rendering drivers; verify units against source when upgrading.
Timestamp queries and inspection add some measurement overhead included in the
complete round trip. Timing intervals do not establish hardware occupancy.

Investigation notes
-------------------
An early shader missed the other body's height in the prior-position rejection
test. The targeted rising-body fixture failed by 0.10912 m before correction;
it and a separate falling-body fixture now pass. Earlier timing artifacts are
exploratory and superseded by the two final runs.

Packing originally constructed four Vector4 values and copied a 64-byte struct
per slot. With the original world delegates, sparse 2,000-body packing took
about 3.54 ms; adding timing wrappers unexpectedly made it much faster. Repeated
alternating tests reproduced the discrepancy. Direct writes into the reusable
buffer remove the constructors/copy and reduce packing to about 0.20 ms without
changing any snapshot hash or parity result. An AVX/SSE transition cost is a
plausible mechanism from the captured JIT code, not a proven general diagnosis.
No wrapper or stub is used in final timings. The optional RunPackingDiagnostics
scene export retains this diagnostic outside measured samples.

contains report.txt, summary.csv, samples.csv and engine logs. Other run labels
and jit-diagnostic.txt preserve the exploratory checks locally.

Transfer and authority constraints
----------------------------------
The default fort allocates 2,000 slots: the corresponding full-capacity transfer
is 128,000 input bytes and 64,000 output bytes per contact call even with fewer
live bodies. The scaling probe fixes allocation at 10,000 and transfers 640,000
input / 320,000 output bytes instead, as reported above.
Run calls Submit, Sync and synchronous BufferGetData. The production sequence
is crowd movement/contacts/attacks, weapon ticks, then deferred death callbacks.
CPU queries therefore expect the newly resolved authoritative positions.

An asynchronous readback is not a drop-in removal of Sync: Godot documents a
frame delay, and combat would receive an earlier position snapshot. A future
pipeline needs explicit simulation tick, world version, slot generation and
mutation version. Generations prevent recycled-slot confusion; mutation versions
also protect living enemies whose positions were changed by pulls, knockback or
teleports after dispatch. Deaths must remain immediate for subsequent queries.

World constraints depend on proposed positions and movement history, not just
the uploaded ground height. They include fort solids, live/restored gates,
support reached from above, ceilings/lintels and rejection of low passages.
They must be serialized and reproduced before multiple GPU steps can advance
independently. Rendering also needs previous/current poses, roll orientation,
role compaction, hit flashes, local-space conversion and conservative bounds.

Next experiments
----------------
1. Repeat the baseline in an exported Release build with the intended runtime
   settings, then profile CPU terrain/fort callbacks separately. The current
   editor's Debug API bindings are a material limitation of these timings.
2. Measure the current per-enemy MultiMesh setters with rendering enabled.
   Compare bulk CPU buffer uploads before testing a GPU transform pass writing
   the main RenderingDevice's MultiMesh buffer. Schedule RD access on the render
   thread; the probe's local-device RIDs and Submit/Sync lifecycle cannot simply
   be reused for the main device. Verify culling and visible-instance behavior.
3. Test evolving ping-pong GPU state on flat ground, then port movement and
   analytic terrain/fort constraints from versioned world data. Preserve bounded
   neighbor order initially, and validate several consecutive steps rather than
   treating repeated frozen-input dispatches as simulation.
4. Preserve CPU health/events and exact combat narrow phases initially.
   QuerySegment supplies capsule candidates; TryEnemySegmentHit computes entry
   distance for exact ordering and weapon/world clipping. Enlarging stale query
   bounds can add candidates but does not preserve exact hit distances. Choose
   an explicit completed authoritative tick shared by rendering and combat, or
   retain CPU authority for interacting enemies, before accepting delayed state.
   Test gate destruction/restoration, piled bodies, projectile sweeps, pulls,
   knockback, chained deaths and visible hit agreement in a live scene.
